# Docker images and GitHub releases

The project builds a static Go binary into a distroless image. The image runs as UID/GID `65532:65532`, includes CA certificates and a readiness healthcheck, and listens on port **18080**. Linux AMD64 and ARM64 are supported. Configuration, signing keys, S3 credentials and uploaded files are supplied at runtime.

## Prepare GitHub

The source repository is [SculkDev/imgserver](https://github.com/SculkDev/imgserver). The workflow in `.github/workflows/distribution.yml` publishes to:

```text
ghcr.io/sculkdev/imgserver
```

The workflow derives the image name from its repository, so forks can publish under their own names too. No personal access token is needed for publishing. The publish job uses `GITHUB_TOKEN` with `packages: write`; application signing keys and S3 credentials do not belong in GitHub Actions secrets because the build does not need them. GitHub organization policies must permit Actions and package creation. If an existing GHCR package already uses the image name, grant this repository Actions access to it.

Pushing the project to GitHub starts the workflow. Preparing these files locally does not publish an image.

## What the workflow does

Every pull request and branch push runs formatting, module verification, `go vet`, race-checked Go tests, Node helper tests, OpenAPI schema validation, and Compose validation. A separate job builds the image and tests non-root execution, a read-only filesystem, the healthcheck, docs, private uploads, and data persistence through a container restart. Pull requests do not log in to GHCR or publish images.

After both jobs succeed, pushes to the repository's default branch publish `edge` and a full-commit `sha-...` tag. A version tag such as `v1.2.3` publishes:

| Git ref | Container tags |
| --- | --- |
| Default branch | `edge`, `sha-<full-commit>` |
| `v1.2.3` | `1.2.3`, `1.2`, `1`, `latest`, `sha-<full-commit>` |
| `v0.2.3` | `0.2.3`, `0.2`, `latest`, `sha-<full-commit>` |
| `v1.3.0-rc.1` | `1.3.0-rc.1`, `sha-<full-commit>` |

`latest` follows the most recently published stable version tag. Prereleases do not move it. Use a full version or image digest for deployments you want to control; `edge`, major/minor aliases and `latest` are mutable. Do not move or reuse existing release tags. Manual workflow runs publish only when run on the default branch or a version tag.

Release images include OCI source/version/revision labels, BuildKit provenance and an SBOM. Official actions are pinned to commit SHAs, and Dependabot is configured to propose updates for Actions, Go, npm and Docker dependencies. Builds cross-compile on the runner's native architecture, so the multi-platform release does not require QEMU.

Push a release:

```sh
git tag v0.1.0
git push origin v0.1.0
```

The workflow publishes on the tag push; creating a GitHub Release separately is optional. Watch **Actions → Test and publish container** for the result, then find the image under your account or organization's **Packages**.

GHCR packages may initially be private. For public distribution, open the package settings and change its visibility to public. A public repository alone does not guarantee an anonymously pullable image. For a private image, consumers need `docker login ghcr.io` using credentials with package read access. See GitHub's [container publishing guide](https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images) and [package visibility documentation](https://docs.github.com/en/packages/learn-github-packages/configuring-a-packages-access-control-and-visibility).

## Run a published image

On the deployment host, obtain these files from the same project version:

- `compose.release.yaml`
- `.env.example`
- `config.local.example.json` for local storage, or `config.example.json` for S3

For a fresh deployment with no existing configuration:

```sh
cp config.local.example.json config.json
cp .env.example .env
chmod 644 config.json
chmod 600 .env
openssl rand -hex 32
```

Put the generated value in `.env` as `IMGSERVER_SIGNING_KEY` and share that key only with your application backends. Set `IMGSERVER_IMAGE` to your actual image, for example:

```dotenv
IMGSERVER_IMAGE=ghcr.io/sculkdev/imgserver:0.1.0
IMGSERVER_SIGNING_KEY=<your-random-key>
IMGSERVER_BASE_URL=https://media.example.com
IMGSERVER_PORT=18080
```

For S3, use `config.example.json` instead of the local template, set the bucket/region/endpoint, and supply AWS credentials in `.env` or through a workload IAM role. Both JSON templates use `"signing_key": "env:IMGSERVER_SIGNING_KEY"`. The JSON contains no secrets and can be readable by the non-root container; keep `.env` private.

If you already have a local `config.json` generated by `imgserver init`, preserve its signing key when migrating: put the existing key in `.env`, replace the JSON signing key with the environment reference, and only then make the JSON readable by UID 65532. Do not overwrite an existing configuration or generate a different signing key during an ordinary upgrade.

When moving an existing native installation into Docker, back up and migrate its `.data` metadata and objects into the named volume before switching. Compose creates a new volume and does not import existing host files automatically. Stop the native instance before starting the container on the same port, and never run two instances against the same SQLite database.

Start the service:

```sh
docker compose -f compose.release.yaml up -d
docker compose -f compose.release.yaml ps
docker compose -f compose.release.yaml logs --tail=100 imgserver
```

Swagger UI is available at <http://localhost:18080/docs>. `IMGSERVER_PORT` changes the host port, while the container port stays 18080. Set `IMGSERVER_BASE_URL` to the address browsers will use, including a non-default port when needed. The port binds to localhost by default; use a reverse proxy for public access and TLS. Set `allowed_origins` in `config.json` to your frontend's exact origin.

The `imgserver-data` named volume persists SQLite metadata and local objects across upgrades. Keep `.data` paths in the supplied configuration so writes go to this volume. S3 deployments still require this volume for metadata. Do not run `docker compose down -v` unless you intend to delete that data. The bind mount fails if `config.json` is missing instead of creating an empty directory.

## Upgrade or roll back

Back up the data volume and, for local storage, all objects in it. For S3, back up metadata and apply your object backup/retention policy too. Change only the image version in `.env`, then:

```sh
docker compose -f compose.release.yaml pull
docker compose -f compose.release.yaml up -d
docker compose -f compose.release.yaml ps
```

For rollback, set the previous compatible tag or digest and repeat. Check release notes for future database migrations before rolling back. For a digest-pinned deployment, `IMGSERVER_IMAGE` can be `ghcr.io/owner/repository@sha256:<digest>`.

Inspect the installed build:

```sh
docker compose -f compose.release.yaml exec imgserver /app/imgserver version
```

## Build and test locally

Prepare the same env-based configuration and `.env` as above, then:

```sh
docker compose up --build -d
```

If another process already listens on 18080, stop it or adjust the host port before starting this source-build Compose stack. The native development server can continue running while the isolated smoke test uses a random host port:

```sh
docker build -t imgserver:local .
node container-smoke.mjs imgserver:local
```

The smoke test creates and removes its own uniquely named container and volume. It never mounts the developer's configuration, credentials or data. Node.js 20 or later and a local Docker engine are required for that test. Use Node.js 24 for the npm development tooling and schema checks:

```sh
npm ci --ignore-scripts
npm test
npm run check:openapi
```

To build a multi-platform image yourself, use a Buildx builder with multi-platform support and export to a registry or OCI archive:

```sh
docker buildx build --platform linux/amd64,linux/arm64 \
  --output type=oci,dest=imgserver.oci.tar .
```

The image contains no shell, package manager or application credentials. Use `docker logs`, `/healthz`, `/readyz`, `imgserver healthcheck`, and `imgserver version` for diagnostics. Temporary uploads use a 512 MiB tmpfs in Compose; tune that limit and upload concurrency for your expected image sizes and host memory.
